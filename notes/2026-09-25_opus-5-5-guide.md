# Claude Opus 5.5 使用指导书

> 来源说明：本文由 Claude 根据 Anthropic 官方 Claude API 文档（Opus 5.5 迁移指南、模型表）整理而成，不是我自己的观点。其中带「Anthropic 测试」字样的数据来自官方表述；标注「上线时待确认」的项目，官方文档自己也写着可能变化。

---

## 一、一句话认识 Opus 5.5

**Opus 5.5 = 更便宜、更省 token、更可靠的 Opus 5。** 它是 Opus 系列的新一代，主打**长时间的 Agent 式编程**和**知识型工作**（分析、报告、审阅）。

| 项目 | Opus 5.5 | 对比 Opus 5 |
|---|---|---|
| 模型 ID | `claude-opus-5-5`（Bedrock 上为 `anthropic.claude-opus-5-5`） | `claude-opus-5` |
| 上下文窗口 | 1M tokens | 相同 |
| 最大输出 | 128K tokens | 相同 |
| 价格（输入/输出，每百万 token） | **$4 / $20** | $5 / $25 |
| 缓存读取 | **$0.20**（基础价的 0.05 倍） | 更贵 |
| Batch 批处理 | $2 / $10 | — |
| Fast 模式（仅 Claude API，研究预览） | $8 / $40（上线时待确认） | $10 / $50 |
| 知识截止 | 2026 年 6 月 | — |
| 默认 effort | **medium** | high |

**关键认知：** 它不只是单价便宜 20%，而是**完成同一任务用的 token 更少**，所以"每个解决的任务"的成本明显更低。

## 二、它最强的能力（以及对你意味着什么）

### 1. Agent 式编程 & Code Review —— 提升最大的领域
- 在真实代码库里做多步任务（改一个功能、一路改到测试全过）：按 Anthropic 测试，**默认 medium 就能达到或超过 Opus 5 在 high 下的效果，步骤更少、token 约省一半**。
- Code Review：**抓到的 bug 更多，误报更少**。
- 会用平实的语言解释自己改了什么，方便你审阅和信任。

👉 **适合：** 交给它一个完整的开发任务让它自己跑完；PR 审查；大仓库里的重构。

### 2. 知识型工作 —— 更靠谱的分析师
- **更少编造**：比 Opus 5 更不容易说出输入材料里没有的数字，或引用错来源。
- 写长篇分析报告：medium 下的质量超过 Opus 5 在 high 下的结果，输出 token 约少 40%。
- 更擅长搭建和**审计财务模型**。
- 对大量材料更细心：比如长邮件线程里一个日期和星期对不上、PPT 里某张图和数字不一致——**而且不会因此乱报一堆假问题**。

👉 **适合：** 读一大堆资料写报告、核对数据、查找文档中的不一致、做尽调。

### 3. 沟通与写作
- 文字更清晰，尤其是汇报工作进展时：**做了什么、发现了什么、需要你做什么**，说得很直白，套话和行话更少。

### 4. 视觉理解 & 电脑操作 —— 质变级提升
- 读图表、示意图、截图更准：按 Anthropic 测试，**即使在 low 档，读图表也比 Opus 5 最高档更准，输出 token 约为其十分之一**（Opus 5 需要写代码裁剪、放大、测量才读得好）。
- 能理解"位置决定含义"的信息：箭头连接了哪两个框、两版架构图之间改了什么、日历截图里会议具体几点开始几点结束。
- 基于截图的多步电脑操作更可靠：默认 effort 就达到 Opus 5 高 effort 才有的成功率，步骤更少、token 约少 40%。

👉 **适合：** 直接扔截图/图表/白板照片给它；自动化操作网页或桌面软件。

## 三、最重要的调节旋钮：Effort（思考力度）

Opus 5.5 **始终开启思考，无法关闭**。你唯一的控制手段就是 **effort**，它同时决定了质量、速度和成本。

| 档位 | 什么时候用 |
|---|---|
| `low` | 简单问答、分类、格式转换、需要快速响应的场景、子任务/子 Agent。很多编程评测上 low 已经接近 Opus 5 的 high |
| `medium`（**默认**） | 绝大多数日常任务的起点。编程、分析、写作都先从这里开始 |
| `high` | 重要且困难的任务，明显感觉 medium 不够时 |
| `xhigh` | 复杂的长程编程/Agent 任务，测过确实有提升再用 |
| `max` | 正确性远比成本重要的时候（不设上限，会很慢很贵） |

### 使用心法
1. **从 medium 开始，往两边试。** 不要想当然地直接开 high/max。
2. **同样档位下，Opus 5.5 比 Opus 5 想得更多**（尤其 xhigh/max）。如果你沿用 Opus 5 的设置，会发现回合更长、token 更多。
3. **想让它少想一点？先降档，别靠提示词。** 降 effort 比写"请简短思考"可靠得多。
4. **想让它"别想了直接答"**：用 `low`，必要时在系统提示里加一句 *"Answer directly without deliberating."*——但要验证质量没掉。
5. **不要写"不要思考"之类的指令**：它做不到，反而会导致输出里泄露内部标签。

> 在 Claude Code 里可以通过 `/model` 或 effort 设置调整；在 API 里是 `output_config: {effort: "medium"}`。

## 四、通用提示词技巧

### 1. 一次性把任务说完整
对长程任务，**一开始就给出完整的任务说明**：目标、约束、验收标准、不能碰的东西。它擅长自己跑很长的流程，前提是它知道"做到什么程度算完成"。

> ❌ "帮我优化一下这个项目"
> ✅ "把 `src/api/` 里所有同步数据库调用改成异步。约束：不改公开接口签名；完成标准：`pytest` 全部通过、`ruff` 无报错。改完用三五句话告诉我改了哪些文件、有什么风险。"

### 2. 重新审视旧模型时代的"补丁式"提示
给 Opus 5 或更早模型写的提示，经常有"控制啰嗦""不要过度验证""不要擅自扩大范围"之类的补丁。**这些在 Opus 5.5 上可能不再需要**，甚至会让效果变差——保留作为起点，但逐条测试，没用就删。

### 3. 前端/设计任务：点名禁止具体样式，而不是说"别太AI"
没有设计方向时，它会落回几种默认风格；说"避免通用 AI 感"只是把一种默认换成另一种。**有效的做法是列出具体要避免的模式，然后迭代：**

> "用原生 HTML/CSS 做一个个人网站，用占位数据。**不要**用米色或灰白背景、标题里的斜体强调词、'01/02/03' 编号的章节标签、等宽字体标签、胶囊形按钮。"

看第一版用了哪些套路，再把它们加进禁止清单。

### 4. 视觉输入：直接给图，别过度加工
- 以前为了让模型读懂图表而做的"预处理脚手架"（先 OCR、先裁剪、先描述）**可能已经不需要了**，重新测试一下。
- 对最密集的图（工程图纸、超密图表）：**提供更高分辨率的图**；如果能给它一个带 PIL / OpenCV 的运行环境让它自己裁剪放大测量，效果更好（effort 越高越会用工具）。

### 5. 需要进度汇报就明说
长任务中它默认会少说话。想要"开工前说一句打算做什么、结束时给个简短总结"，**直接在系统提示/指令里写清楚你想要什么时候汇报、汇报什么内容**。结对编程、人在回路中的工作最受益。

### 6. 让它自己验证
给它可以跑的检查手段（测试命令、lint、对账公式），并把"验证通过"写进完成标准。它对细节很敏感，但你得告诉它用什么来证明做完了。

## 五、分场景使用手册

### 场景 1：日常编程（Claude Code）
- **推荐 effort：** medium 起步；大型重构/跨模块任务用 high 或 xhigh。
- **做法：** 把需求、约束、验收命令一次说清；让它自己跑测试直到通过。
- **示例 prompt：**
  > "修复 issue #42 描述的登录超时问题。先复现，再定位根因，再修复，最后跑 `npm test` 确认。不要改动 `auth/legacy/` 目录。结束时告诉我根因是什么。"

### 场景 2：Code Review
- **推荐 effort：** medium～high。
- **做法：** 给它 diff 或 PR 链接，说清关注点（正确性 / 安全 / 性能），要求按严重程度排序、每条给出具体触发场景。它的误报率比以前低，值得信任它的高优先级发现。
- **示例 prompt：**
  > "审查这个 PR，只报告正确性和安全问题，按严重程度排序。每个问题写：文件行号、什么输入会触发、后果是什么。不确定的单独列出。"

### 场景 3：研究分析 & 报告写作
- **推荐 effort：** medium（长报告已经优于 Opus 5 的 high）。
- **做法：** 把原始材料全部给它（1M 上下文足够装很多文档），要求**每个关键数字标注来源**。它更不容易编造，但让它标来源能让你快速核查。
- **示例 prompt：**
  > "基于这 12 份季度财报，写一份竞争格局分析。每个数字后面用括号注明出自哪份文件哪一页。材料里没有的信息，明确写'材料未提及'，不要推测。"

### 场景 4：数据核对 & 找不一致
- **推荐 effort：** medium～high。
- **做法：** 这是它新增的强项。让它查"日期和星期是否匹配""图表和正文数字是否一致""财务模型公式是否有错"。
- **示例 prompt：**
  > "检查这份 40 页的投资备忘录：所有图表是否和正文数字一致、所有日期是否正确、计算是否能对上。只报告真正的问题，每条给出页码和证据。"

### 场景 5：读图表、截图、架构图
- **推荐 effort：** low 就很好用了！密集技术图纸再调高。
- **做法：** 直接上传图片，不用预先描述。
- **示例 prompt：**
  > "这两张是 v1 和 v2 的系统架构图，列出所有变化：新增/删除的组件、连线的变化、方向的变化。"
  > "这是我下周的日历截图，列出每个会议的准确起止时间，找出有冲突的时段。"

### 场景 6：电脑操作 / 浏览器自动化
- **推荐 effort：** 默认 medium 即可。
- **做法：** 用新的 computer toolset（见第六节 API 注意事项）；给清晰的目标和停止条件。
- **示例：** "打开后台管理系统，把所有状态为'待审核'且超过 7 天的订单导出成 CSV。遇到需要登录或付款的页面立刻停下来问我。"

### 场景 7：写作 & 汇报
- **做法：** 它现在的默认文风已经比较直白。给出读者是谁、用途是什么、长度要求即可；如需特定风格，给一段范例比形容词更有效。
- **示例 prompt：**
  > "把这次项目复盘写成给老板的一页纸：结论先行，做了什么、结果如何、下一步要什么支持。不要用'赋能''抓手'这类词。"

### 场景 8：个人知识库（比如这个 OpenNote 仓库）
- **记录：** 发文字/图片/链接，它会按 CLAUDE.md 的规则落盘、提交、推送。图片记录尤其受益于它更强的读图能力（白板、截图、手写笔记都能准确提取）。
- **探索：** 让它"扫描本月笔记摘要，找出反复出现的主题"——它先看 frontmatter 摘要再按需深读，1M 上下文也能一次读很多笔记。它更少编造的特性让"洞察"更可信，但仍建议要求它**引用具体笔记文件**。

## 六、开发者专区：通过 API 使用的注意事项

如果你是用 API 调用（而不是在 Claude Code / claude.ai 里用），以下是从 Opus 5 迁移过来的**四个破坏性变更**：

1. **思考无法关闭。** `thinking: {type: "disabled"}` 和 `{type: "enabled", budget_tokens: N}` 都会返回 400。直接省略 `thinking` 参数（或设为 `{type: "adaptive"}`），用 `output_config.effort` 控制。
   - `max_tokens` 要给思考留空间（思考计入 `max_tokens`），长程编程任务 64K 是不错的起点。
   - 按 block 的 `type` 读取响应，不要按位置取第一个块——开头可能是 `thinking` 块。
2. **不支持强制工具调用。** `tool_choice: {type: "any"}` 或 `{type: "tool", ...}` 返回 400。改用 `auto` + 工具定义上加 `strict: true` + 在提示里明确要求使用该工具，并**检查确实调用了、没调用就重试**；如果只是为了拿 JSON，改用结构化输出 `output_config.format`。
3. **思考块绑定模型和对话（preserved thinking）。** 历史消息（system、tools、之前的消息）必须保持逐字节不变，否则回放的思考块会失效；2026-08-31 之后创建的账户默认强制校验（会 400）。做法：只追加、不修改历史；中途要加指令就追加一条 `role: "system"` 消息；所有可能用到的工具在会话一开始就声明。
4. **电脑操作只支持新 toolset。** 用 `{"type": "computer_toolset_20260801"}`（无 name、无分辨率参数），旧的 `computer_20251124` 会 400。Agent 循环也要改：动作名在 `tool_use` 块的 `name` 上，一轮可能有多个动作，每个结果都要带 `"toolset_name": "computer"`。

**其他要点：**
- **默认 effort 是 medium**（Opus 5 是 high），要显式设置。
- **工具调用之间的文字**现在以 `thinking` 块返回，默认内容为空。如果你的界面需要显示进度，设 `thinking.display: "updates"`（beta）。
- **安全分类器更广：** 新增 `bio`（两用生物研究）和 `reasoning_extraction`（诱导它把内部推理写进回复）。响应可能是 HTTP 200 但 `stop_reason: "refusal"`——**先检查 `stop_reason` 再读内容**，并开启服务端 fallback（`fallbacks: "default"`），避免误判变成故障。想看推理过程，用 `display: "summarized"`，别在提示词里要求它"把思考过程写出来"。
- **缓存更划算：** 缓存读取只要 $0.20/M，长会话保持缓存命中（只追加历史、用 per-message effort 而不是改顶层 effort）收益更大。
- **不支持：** assistant 预填（prefill）、`temperature`/`top_p`/`top_k`、Priority Tier。

最小示例（Python）：

```python
import anthropic

client = anthropic.Anthropic()
with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=64000,
    output_config={"effort": "medium"},
    messages=[{"role": "user", "content": "..."}],
) as stream:
    response = stream.get_final_message()

if response.stop_reason == "refusal":
    ...  # 处理拒答 / 走 fallback
else:
    text = "".join(b.text for b in response.content if b.type == "text")
```

## 七、常见误区清单

| 误区 | 正确做法 |
|---|---|
| 一上来就开 max，觉得越高越好 | 从 medium 开始，测过有提升才加档 |
| 嫌它想太久，就在提示里写"别想太多" | 直接降 effort |
| 沿用旧模型的一堆约束性提示 | 逐条测试，不需要就删 |
| 让它"做个好看的页面，别有 AI 味" | 列出具体要避免的样式，并迭代 |
| 截图先 OCR 再喂给它 | 直接给原图，高分辨率更好 |
| 任务说一半，边做边补充 | 一开始就给完整目标、约束、验收标准 |
| 相信它不会出错，不要求来源 | 让它标注来源 / 跑验证，方便你快速核查 |
| API 里修改历史消息来"注入提醒" | 只追加消息，用中途 system 消息 |

## 八、一页速查

- **默认就用 medium**，简单快任务用 low，难题再往上加。
- **任务一次说完整**：目标 + 约束 + 验收标准。
- **给它验证手段**：测试、lint、对账方式。
- **视觉任务直接给图**，low 档就很强。
- **前端设计点名禁止具体样式。**
- **分析报告要求标注来源。**
- **想要进度汇报就明说。**
- **API：** 不能关思考、不能强制工具、历史只追加、电脑操作用新 toolset、先查 `stop_reason`。
